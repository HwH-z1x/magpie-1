# Magpie 每请求意图路由与定制版本维护执行计划

状态：已进入实现。主体保留初始方案；当前进度和用户新增约束见末尾执行记录。日期：2026-10-22（Asia/Shanghai）。

本文用于实施和验收个人定制版本。文中的新字段、测试名和脚本接口均为拟议设计，不能当作当前 Magpie 已有功能。当前行为与拟议行为分开记录；正式实现后，再同步对应的子系统设计参考。

## 1. 项目目标

在同一轮对话内，Agent 每次向 Magpie 发起新的模型生成请求，包括携带工具结果的后续请求，都根据请求到达时的任务状态重新判断意图，再按已有路由组规则选出合适成员。

例如，用户只发送一次“修复问题并验证”，后续请求可以依次分配给排查模型、代码模型、测试分析模型；不需要等用户再次发言。重新分类不保证每次换模型，任务状态相同或分类器判断相同时，可以继续选择同一成员。

继续使用 Magpie 的路由组、分类模型接入、规则匹配、嵌套分组、候选排序和故障转移。分类输入、判断频率和缓存策略需要适配“当前请求下一步要做什么”。通过现有路由记录向 GUI 展示实际分类、选择和故障转移过程。

同时建立 Windows 定制 exe 的构建与更新流程：上游变化先进入候选工作区，经过验证后才部署；冲突、测试或构建失败时，正在使用的版本继续运行。

## 3. 当前行为与改动依据

开始实现前阅读 [子系统索引](subsystems/README.md)、[路由设计参考](subsystems/gateway-routing.md)、[代码标准](code-standards.md) 和 [LESSONS.md](../LESSONS.md)，并跟踪下列实现。

| 当前机制 | 源码入口 | 对本项目的影响 |
| --- | --- | --- |
| 工具结果仍属于同轮 | [`turnIn`](../internal/gateway/affinity.go) | 后续请求不会自然触发新轮次分类 |
| 同轮返回先前规则结果 | [`ruleFor`](../internal/gateway/rules.go) 的 `within` 分支 | 仅关闭会话保持无法改变它 |
| 规则可能用不到意图时不调用分类器 | [`provider.Intents`](../internal/provider/grouprule.go) | 即使绕过同轮分支，也不能承诺每个请求实际调用分类模型 |
| 相同分类输入缓存 10 分钟，并合并并发相同问题 | [`classify`](../internal/gateway/classify.go) | 必须区分执行分类流程与实际发起分类调用 |
| 分类器失败后暂歇 30 秒 | `classifyRest`、`classified.failed` | 严格每请求尝试模式不能继续被此层直接短路 |
| 分类主体只取最后一条用户自己的文字 | `userText`、`turnBefore` | 工具调用和结果不会让分类器理解本轮阶段变化 |
| 账号/Key 保持是另一层决策 | [`Group.Affinity`](../internal/provider/group.go)、`affine` | 新规则结果还必须通过候选排序真正生效 |
| 嵌套分组分别判断规则 | `nestedRules`、`ruleOver` | 不能只修改最外层分组 |
| 规则和自动判断可改变推理强度 | `keepsEffort`、`ruleEffort` | 要记录分类器所选值与实际发送值的差别 |

当前分类器可沿已有路径使用普通聊天模型、专用决策模型和决策模型分组。普通模型在同时判断意图和推理强度时，`askClassifier` 会并行发起两类调用。因此“一次逻辑分类”不等于“恰好一个物理 HTTP 请求”。

## 4. 行为合同

### 4.1 适用请求与计数

“每请求”指客户端新到达、经现有鉴权和安全检查允许继续、能解析并进入目标路由组的模型生成请求。包括首个用户请求、同轮工具结果续接、Agent 自动继续，以及经该路由组处理的压缩生成请求。

不把以下事件计成新的分类触发：响应流的 chunk、同一个入站请求内部的供应商重试、账号切换或故障转移。客户端自己重试形成新的入站请求时，则重新分类。

模型列表、健康检查、token 计数、独立搜索/图片/音频/embedding 等旁路接口，不在首期“每生成请求分类”范围内。直接请求具体模型且不解析为路由组时也不额外分类。实施时列出实际支持的 HTTP 路径，以集成测试证明 Chat、Responses、Messages、Gemini 的路径都覆盖到。

对每个实际参与决策、配置了意图规则和有效分类器、开启 request 模式的分组，每个适用请求发起一次新的逻辑分类。即使输入与前次相同也实际尝试；不使用跨请求的成功结果缓存或相同输入并发合并。一个入站请求经过多个 request 分组时，可以产生多次逻辑分类，不能把它误算为一次。

分类器自己的内部请求保留递归保护，不再次触发分类；所有专用决策后端也必须验证这条约束。手动路由仍按用户手动选择处理，界面明确该模式不启用意图选择。没有意图规则的分组不产生有意义的意图分类，界面禁用该开关或明确提示；只有自动推理强度时可单独重新判断强度，但不能标记为已判断意图。

### 4.2 分组配置

拟议字段：`ruleScope`，JSON 类型为字符串，值如下。

| 值 | 行为 |
| --- | --- |
| 缺省或 `turn` | 保持当前按轮判断行为和优化 |
| `request` | 每个适用请求重新判断并应用规则 |

建议 Go 字段 `RuleScope string`，采用 `json:"ruleScope,omitempty"`；存储时可将 `turn` 规范化为空，读取空值视为 turn。未知值保存时报错；磁盘已存在未知值时按仓库已有错误处理方式报告，不偷偷启动 request 行为。

每个嵌套组独立使用自己的配置，不隐式继承父组的 request 设置。用户要全链路每请求重判时，应开启会参与决策的各级分组；GUI 提示尚按轮运行的子组。模板新建仍默认 turn，复制现有组保留其设置。

CLI 拟议语法：`magpie group set <id> rule-scope=request`。需要同时支持读取、设回 turn、帮助文本和非法值校验。GUI 在规则/分类器设置附近提供“按轮 / 每请求”，与“会话保持”分开。

此字段需贯穿 providers.json、GUI API、编辑保存、卡片上的快捷保存、复制、重命名、分享/导入，以及现有备份/同步路径。旧版可能忽略新字段，之后保存又将它丢失；不承诺旧版保留 request 设置，降级前必须备份。

### 4.3 严格调用与规则优先级

request 模式不能只调用现有 `provider.Intents`：该函数遇到前置无意图规则会提前终止，可能跳过分类。

拟议处理：收集当前分组全部有效的非 pause 意图规则，按原顺序、忽略大小写去重，作为分类候选；再将分类结果送回原有 `MatchRule` 和 `ThenUses`。即使某意图规则的其他条件暂时不满足，也允许分类器描述当前请求意图，最终是否路由到它仍由全部规则条件决定。

这样可以每次调用分类器，同时保留“第一条匹配规则优先”的意义。若第一条无意图规则已经匹配，分类仍执行，但该规则仍可能决定最终成员；GUI 应清楚区分“分类结果”与“命中的规则”。想让意图主导选择时，应将意图规则排在通用兜底规则之前。

turn 模式的 `provider.Intents` 优化保持原状；不全局改成每次调用。

### 4.4 每次判断看到的内容

目标是判断“现在接下来的模型工作”，而非只重复识别最初用户消息。复用分类模型接入、候选编号、答案解析和错误路径，但增加 request 模式的输入构造与提示说明。

建议首版使用有界的当前轮状态，不依赖内存计算请求差分：

1. 当前轮用户的真实需求，沿用 `userSaid` 的去注入逻辑，上限 4000 个 Unicode 字符。
2. 当前轮最近的工具调用与结果，包含工具名、调用关联、适量参数、成功/失败和输出文本，合计上限 6000 字符；优先保留最新结果，再向前补齐对应调用。
3. 当前轮最新可见的助手文本，上限 2000 字符；保留现有上一轮背景能力，但纳入总预算，不无限追加。

整个输入预算初拟 12000 字符，包含上一轮背景、结构标记和截断说明；各部分是上限，必须在序列化后再次检查总长。按完整工具记录分配预算，单条超长内容用确定的头尾截断，标明截断，不让陈旧的大输出挤掉最新错误。并行工具结果尽量保留每项状态。具体预算在离线用例中验证后确定，不宣称字符数等于 token 数。

不传系统提示全文、推理正文、加密推理、签名、凭据、图片 base64 或二进制文件；图片/文件只有必要的类型标记。找不到调用上下文时保留结果的有限文本和“工具未知”状态，不猜工具名。无文字但有图片/文件的请求仍提供结构性描述，分类器不具备图像理解时不声称已理解图像内容。

工具输出和检索内容必须作为待分析数据传入，不能成为分类指令。普通聊天分类器和专用决策后端的输入都要适配；不能只修改聊天提示而让 Jev/System One 继续看旧输入。新的结构性提示说明用户需求、当前执行状态、候选意图各自含义。

沿用 Magpie 的 Privacy 策略，验证新增参数和工具结果在发送分类器前经过现有脱敏链。当前存在显式不脱敏的路由选择，需确认普通模型请求与分类请求分别采用什么策略，不把所有解析出的 body 都假设为已脱敏。新增上下文不得绕过分类请求自身的隐私处理，也不得在路由记录中持久化完整工具输出。

### 4.5 缓存、失败与重试

request 模式需要独立的调用策略，避免改坏 turn 模式的缓存和并发测试：

- 不读取或写入跨请求成功结果缓存，不与其他入站请求合并分类调用。
- 不因 `classifyRest` 在分类层直接跳过本次尝试；保留失败诊断记录。
- 同一请求内部复用已经得到的分类结果完成所有供应商尝试，不在故障转移循环中重新分类。
- 超时、错误答案或无法获取分类服务时，保留现有“上一有效意图仍在候选内则沿用，否则无意图匹配”的降级思路，并显式记录失败和降级。
- 检查当前各分类后端的超时是否可累加；在 request 路径把入站取消传播给分类调用，客户端离开后及时停止。不要把现有单次调用 8 秒超时误称为整个入站请求的总延迟上限。
- 沿用分类器所依赖网关的账号休息、限额、允许列表和安全约束。网关可能因没有可用候选而在本地拒绝；这仍算本次尝试失败，不能声称已收到新的模型判断，也不能强行绕过供应商限流。

严格模式承诺每次发起新的分类尝试，不承诺供应商每次成功作答。记录至少区分“尝试过并回答”“尝试过但失败”“不适用/无法解析”“递归保护”。

初版沿用现有自动推理强度的缓存保温策略：即使重新判断出较低强度，实际发送值仍可能因 `keepsEffort` 保持较高。界面分别展示判断值与实际值；模型成员选择必须服从本次有效规则结果。若后续需要连推理强度也每次无条件降低，另立需求和测试，不悄悄扩大此次行为变化。

### 4.6 候选排序、嵌套与请求状态

request 模式绕过“同轮直接返回”，但保留真实轮次统计、会话身份以及供应商输入 token 等统计。不能通过伪造新用户轮次或清空整个 `turnRules` 实现。

新结果必须以本次请求局部状态贯穿 `ruleOver`、嵌套组、`ThenUses` 和 trace；不能被旧 `Held`、`Waits`、故障接手记录或旧亲和性重新覆盖。普通亲和性仍可在本次选中成员的账号范围内发挥作用。`strict` 或显式账号固定等硬约束如与换成员冲突，界面说明并拒绝不兼容配置，或按已有硬约束拒绝请求；不得静默越过固定账号。实施前以测试确认具体冲突位置。

同一会话的并行请求必须各用自己的分类结果。更新共享的“最近意图”时防止早到但晚完成的旧请求覆盖更新的状态；可采用请求序号或版本检查，在实现阶段选最小方案。网络调用不放在共享锁内。可恢复状态用于失败降级，不用于跳过后续分类。

压缩生成请求在 request 模式下也执行分类，然后沿已有 compact 规则的容量筛选选择；需明确原来早返回的位置，避免漏判。上下文不能容纳、模型未启用、暂停、额度耗尽、供应商不接受跨模型历史等约束继续通过已有候选过滤和失败路径处理。分类不能保证任意两个模型的私有推理/会话格式可互换，必须做实际协议用例验证。

## 5. 路由页面与可观察性

使用现有核心网关和 trace，保留页面的 Agent → Magpie → 成员动画；新增标记解释每请求重判，不另做假动画。动画、请求明细和用量的正确性要通过 GUI 和端到端验证后才算交付。

拟议在 `RuleHit`/`Classified` 增加必要的兼容字段，具体命名在实现时定稿：

- 判定范围 `turn`/`request`，本次是否真实尝试分类、是否成功及耗时。
- 输入类型“用户需求 + 当前轮状态”，以及是否截断，不展示或落盘完整敏感上下文。
- 本次意图、匹配规则、优先成员、最终回答成员、分类失败与降级原因。
- 请求模式下 `Cached` 不能谎报命中；旧 `Held` 文字不能描述本次新判断。
- 分类器自己的请求延续 `routing` 用途和 Magpie 自用计费标记；普通模型同时判断强度时可能有两条分类调用，展示数量如实反映。

当前路由界面实现在 `internal/gui/assets/plugins/routing/`。这里属于 Magpie 自带路由界面代码；对其作必要修改不意味着改用外部插件实现路由。

## 7. 验收与验证矩阵

首要证据是一个真实网关栈的本地集成用例：同一 session、同一轮用户消息，连续发送用户请求和两次工具结果请求；fake 分类器分别返回三种意图，fake 上游记录实际收到的成员。断言三次独立逻辑分类、三次对应选模，且用户轮次只增加一次。

所有测试使用本地 fixture/httptest，不访问实际供应商或真实 Agent 配置。以下名称仅作拟议测试说明。

| 场景 | 必须证明 |
| --- | --- |
| 同轮工具循环 | `TestRequestIntentRoutesEachToolContinuation`：每次分类并正确选模 |
| 完全相同输入 | 仍有两次调用，未命中 10 分钟缓存 |
| 并发相同输入 | 各自调用，不共享结果；完成顺序颠倒也不串路由 |
| 分类器先失败后恢复 | 下一请求立即重新尝试，不被 30 秒分类冷却短路 |
| 工具阶段变化 | 用户需求不变、工具结果变化时，分类器实际收到不同当前状态 |
| 规则优化 | 前置无意图规则不跳过严格分类，但最终仍遵守第一匹配规则 |

## 8. GitHub 与分支管理

目标 fork 拟定为 `HwH-z1x/magpie`，维护分支 `custom/request-intent`。这两个是计划值，本文没有创建它们。

当前上游无写权限，不能直接在 `yetone/magpie` 创建分支。插件可以读写现有授权仓库，但本次工具集中未提供创建 fork 的接口。先在 [上游 Fork 页面](https://github.com/yetone/magpie/fork) 建立个人 fork，并使 GitHub 插件可以访问它；fork 已存在但未授权时只需补齐访问，不重复创建。

之后从 fork 的真实基线创建 `custom/request-intent`，记录 fork 的 HEAD 和所对应 upstream SHA。若 fork 落后，先在候选区合并并验证；不要把旧快照整目录覆盖到 fork。原桌面快照保留作比对，采用新增 Git checkout 工作，不直接覆盖来源不明的本地文件。

推荐关系：`origin` 指个人 fork，`upstream` 指 `yetone/magpie`。fork 的 `main` 尽量保持上游镜像，定制修改提交到维护分支。远端文档提交只包含本项目文档；不提交账号、便携 data 或构建缓存。

长期已推送的维护分支默认用 merge 接入上游，避免每次更新都重写已发布历史。rebase 可用于尚未分享的短期开发分支；如未来决定重写远端历史，需明确用途、备份分支并采用 lease，而非自动强推。脚本不强制选择 rebase。

每次更新记录源基线 SHA、上游目标 SHA、定制提交或合并 SHA、检查结果、exe SHA256 和构建工具链版本；上游接收等价功能后，再评估删除本地重复修改。

## 9. Windows 构建与运行

安装与当前源码 `go.mod` 匹配的 Go 工具链，先验证干净上游能够构建，再做功能修改。make 可选；Windows 桌面发布路径使用 WebView2，Makefile 的 `release-windows` 采用 `CGO_ENABLED=0`。

在实际 Git checkout 中的构建示例（不是本文已执行的结果）：

```powershell
$env:CGO_ENABLED = '0'
$customCommit = git rev-parse --short=12 HEAD
if ($LASTEXITCODE -ne 0) { throw 'Cannot read source commit' }
New-Item -ItemType Directory -Force -Path .\dist | Out-Null
go build -tags production -trimpath -ldflags "-s -w -H windowsgui -X main.version=custom-$customCommit" -o .\dist\magpie-custom.exe .
if ($LASTEXITCODE -ne 0) { throw 'Build failed' }
```

构建脚本应保存并恢复环境变量，并拒绝未提交的发布源码；示例只展示核心命令。正式发行版还生成 `build/windows/winres.json` 对应的图标、版本和 DPI manifest。构建需按官方路径加入资源并检查 Windows DPI/GUI 行为，不能把未加资源的裸构建视为完整发布验证。

用 `custom-<sha>` 版本标识并验证 `update.Released` 返回 false，防止普通官方升级替换定制 exe。不要把正式上游版本号原样赋给定制二进制。配置也要关闭或正确处理官方安装/升级入口；以测试确认桌面端行为，不能只检查 CLI。

正式使用前，通过托盘退出占用默认网关的官方版；启动定制版 `magpie-custom.exe gui`。脚本启动后台 GUI 时使用 `Start-Process -WindowStyle Hidden`。默认数据位置由 `appdir` 决定；exe 旁有 `.portable` 等标记时使用便携 data。部署前检测官方 exe 实际是否处于便携模式，不能一概假设数据在用户配置目录。

初次隔离验证使用新的独立运行目录、`.portable` 和测试 data，不让测试读写真实配置。正式 exe 放在固定运行目录，源码 checkout、候选 exe、历史版本与 data 分开，构建更新不清理 data。Windows 更新期间启动项和桌面快捷方式也应最终指向固定路径，避免登录后又启动官方版。

## 10. 更新脚本合同

拟议脚本 `build/update-custom.ps1`，默认只检查更新。`-Build` 构建候选，`-Deploy` 显式部署已验证候选，`-Rollback` 回退到上一个部署；接口名称在实现时定稿。本次不建立定时任务。

### 10.1 获取与集成

1. 校验绝对源码/构建/运行路径、Git remotes、分支、干净工作区及无进行中的 merge/rebase；获取进程锁，拒绝并发更新。
2. `git fetch upstream` 后固定目标 SHA，不以执行途中继续变化的 `main` 为构建身份。可支持选择稳定 tag，但必须记录实际 SHA。
3. 保存现有维护分支基线；在本次更新专属 worktree 和候选分支中合并该 SHA。共享维护分支在此阶段不移动。
4. 冲突时停止，保留候选 worktree 和冲突清单供修复。主运行程序不受影响，不自动覆盖冲突文件或把冲突当成没有更新。
5. 所有 Git/Go/Node 原生命令检查退出码；PowerShell 的 `$ErrorActionPreference = 'Stop'` 不能代替 `$LASTEXITCODE` 检查。

### 10.2 验证与打包

1. 在候选源码上完成第 7 节的检查，产出机器可读验证清单；未完成必要平台检查的候选不标记可部署。
2. 构建到独立候选目录，生成版本、资源、SHA256 和源提交映射，不能直接覆盖运行中的 exe。
3. 在全新隔离 data 和独立端口启动候选，检查健康、版本/构建身份和同轮多请求路由回归。仅健康检查 200 不足以证明是新程序，更不能探测到旧网关就判成功。
4. 记录候选结果，只有明确测试通过的候选才能进入部署。构建后源提交发生变化，验证失效，必须针对新提交重新验证。

### 10.3 部署与回滚

1. 在停止程序前已完成耗时验证，部署只做短暂停机操作。按已配置 exe 的绝对路径和 PID 定位目标进程，优先正常退出；文件仍被占用则停止部署，不按名称杀掉所有 Magpie。
2. 停机后备份完整配置/便携 data，并保留旧 exe、校验值和构建清单。上游可能迁移数据，因此“换回旧 exe”不保证数据兼容；需要连同部署前数据快照恢复。备份应保留现有账号和文件权限。
3. 候选复制到运行目录同一文件系统，再采用 Windows 支持的替换操作保留旧文件备份；替换失败直接恢复旧程序，不先删除唯一可用 exe。单次文件替换可原子化，但“exe + data + 启动”整体不能承诺原子事务。
4. 启动目标 exe，核对新进程路径、版本/构建身份、网关归属和健康；失败时停止新进程，恢复旧 exe 及必要数据快照，重新启动旧版。
5. 成功后在本地维护分支仍与部署前基线一致时推进它；推送仅限个人 fork，拒绝意外远端变化和强推。远端推送失败单独报告，不假称已经同步，也不随意删除正在使用的构建。
6. 清理只针对本次脚本创建且确认不含用户改动的候选文件；失败诊断保留。任何 Windows 递归删除前核对解析后的绝对路径确实位于专属目录，不能拼接跨 shell 的删除命令。
