# 每请求意图路由：定制版操作说明

本说明对应 `HwH-z1x/magpie-1` 的 `main` 分支（本地开发工作区位于 `custom-src`，上一级目录保留原始源码快照）。按项目约定未新增或修改测试文件；现有检查可正常执行，但新增的“每请求”模式尚未编写专门的自动回归测试。

## 使用

在“路由”页面编辑目标组，将“规则判断频率”设为“每请求”，配置分类模型和意图规则后保存。不带意图的通用兜底规则应放在意图规则之后，否则会按第一条匹配规则直接命中通用规则。

开启后，同一轮返回工具结果时也会重新调用分类器。分类输入包含用户原始任务、最近最多 12 条工具调用与返回结果（含报错状态）以及可见助手文本，受长度预算限制，不包含推理签名或二进制附件。与靠 Agent 派发子代理（Subagent）不同，“每请求”模式不需要主代理主动新建支线会话，无论主代理还是子代理自身的工具循环，都会在同一段上下文里按最新执行状态重新匹配规则。相同输入不跨请求复用本地 10 分钟分类缓存，单次分类失败也不会让分类层进入冷却而跳过下一请求；供应商或账号自身的冷却、额度和固定账号限制仍然有效。

每请求判断不代表每次都会切换模型，也不保证每次分类都成功。分类失败时可沿用最近一次有效意图，并在路由记录中注明原因。分类器的推理强度判断仍受原有缓存保温策略影响，可能维持较高强度。每次额外分类都会带来延迟、token 消耗以及潜在的提示词缓存损失。

嵌套子组各自独立设置判断频率；如需全链路按每请求判断，需对参与路由的各级分组分别开启。手动路由保留手选模型。同一路由组不能同时开启“严格会话保持”和“每请求”规则判断，普通会话保持仍可用于组内同一模型的账号选择。模型列表、健康检查等非生成接口不触发分类；分类器自身的请求不会递归分类，单次入站请求内部的供应商重试也不会重复分类。

也可以用命令行切换：

```powershell
.\dist\magpie-custom.exe group set <组ID> rule-scope=request
.\dist\magpie-custom.exe group set <组ID> rule-scope=turn
```

路由页面动画直接读取核心网关的真实记录，请求明细会标注当次请求的分类结果、耗时、输入截断或回退原因，无需安装额外的外部路由插件。

## 构建

源码所需的 Go 版本以 `go.mod` 为准（当前为 Go 1.26.8，本地便携工具链与缓存位于上一级 `.toolchain/go`，不改动系统 Go 环境）：

```powershell
$env:CGO_ENABLED = '0'
..\.toolchain\go\bin\go.exe run github.com/tc-hib/go-winres@v0.3.3 make --in build/windows/winres.json --arch amd64,arm64 --out rsrc --file-version 0.0.0 --product-version 0.0.0
..\.toolchain\go\bin\go.exe build -tags production -trimpath -ldflags '-s -w -H windowsgui -X main.version=custom-request-intent-dev' -o dist/magpie-custom.exe .
```

手动开发构建使用 `custom-<sha>` 版本号并显示手动维护提示。GitHub 发行构建使用独立递增的 `1.0.N` 版本号，同时嵌入上游版本号与源码提交；只有具备完整发行元数据的受支持平台才会启用分支在线更新。程序入口始终启用分支保护，拒绝切回官方更新源。运行前请先退出占用默认 3425 端口的官方版。

首次使用建议将 exe 放入专属目录，并在同目录新建 `.portable` 文件，使配置保存在同级的 `data` 目录中。便携模式会建立独立配置，不会自动读取官方版账号；如需迁移，请先退出官方版并备份其数据目录，再通过 Magpie 的备份与恢复功能导入。

## 获取上游更新

### 软件里的“重启更新”如何处理

Windows x64 分支发行版只从本仓库的专属渠道检查、下载并重启更新。GitHub Actions 会先合入上游正式版源码并编译出带每请求路由功能的完整 exe，用户本机无需编译源码。详情见[分支发行与重启更新](custom-release-channel.zh-CN.md)。从原版或本地开发版切换过来时，需手动下载替换一次发行版；之后即可直接在软件内点击“重启更新”。

开发构建或未提供发行包的平台仍提示手动维护，`update` 命令不会直接覆盖二进制。发行构建的 `update check` 与 `update` 均绑定分支专属渠道，即使环境变量指定了官方更新地址也不会切回官方源；退出时安装和管理员提权替换同样经过校验保护。

这层保护只作用于当前进程。系统里残留的另一份官方 Magpie、外部安装器或指向原版的快捷方式仍可能启动原版程序。首次切换时请退出原版、备份数据并检查快捷方式。重启更新可在新二进制无法启动时恢复旧二进制，但不负责回滚配置数据迁移。

下方的 PowerShell 脚本供本地离线维护或开发调试使用，不参与线上自动发行流水线。

### 合并源码与构建候选

`origin` 指向个人 fork，`upstream` 指向 `yetone/magpie`。先提交本地定制改动，再执行：

```powershell
.\build\update-custom.ps1 -Action Check
.\build\update-custom.ps1 -Action Build -Go 'C:\Users\Hao\Desktop\magpie-main\.toolchain\go\bin\go.exe'
```

Build 在 Git 内部目录创建独立候选 worktree，合并固定的上游 SHA，运行已有 Go suite/vet，生成 Windows 资源和 exe。冲突时保留候选区并停止；源分支和正在使用的程序保持原样。候选目录包含 `manifest.json` 和校验值。

清单的 `remainingChecks` 列出 GUI、Linux、race、隔离 Agent 实测等未执行项；由维护者完成并记录实际结果后清空，才能部署。不能因只做了 Windows 构建就清空列表。脚本保留所有候选与诊断，不自动清理历史版本，不自动推送 GitHub、不建立定时任务，也不自动推进源码维护分支。

若候选验证合格，先在干净源码工作区合并候选清单里的 commit 并核对身份，再推送个人 fork。冲突解决或任何追加改动都需要重新构建验证，不能沿用旧候选清单。

## 部署与回退

脚本部署仅管理显式指定、已有 `.portable` 标记的专属便携目录，使用默认网关端口 3425。它不自动接管官方安装目录或其他数据位置。

```powershell
.\build\update-custom.ps1 -Action Deploy -Candidate '<候选package目录>' -RunDirectory '<专属运行目录>'
.\build\update-custom.ps1 -Action Rollback -RunDirectory '<专属运行目录>'
```

脚本只定位该路径的 `magpie-custom.exe`，请求正常退出；托盘程序不退出时提示手动退出，不强杀。停机后复制完整 data 并保留旧 exe，再在同卷替换文件；启动时检查网关监听进程归属和健康。新版本失败时尝试还原旧 exe 和部署前数据，若失败进程仍占用文件则停止并保留回滚状态，需退出程序后显式 Rollback。

`.backups` 保存部署前状态，`.failed-*` 保留回退时较新的数据。回滚会恢复部署前数据，之后产生的会话变化不会自动合并，但仍保存在 failed 目录。首次部署没有旧 exe 时回滚只恢复原来的空安装状态。不要删除备份直到确认新版本和数据正常。

当前脚本已经过语法解析；未在用户实际安装或账号上执行部署/回滚演练。它还需要在隔离便携目录中验证后才能用于日常更新。
